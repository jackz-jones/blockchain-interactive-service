## 1. 触发判定（低风险小改动）

02 Plan 阶段按「前置短路 → 逐维度核对（范围 / 逻辑 / 契约 / 风险 / 测试覆盖）→ 输出判定」评估本次改动——**未触犯任何排除项时可采用（行数不作判据）**，`00-overview.md` Meta `小需求模式` 设为 ✅，按 `AGENTS.md`「执行规则」执行；该标记不扩大授权或自动跳过 IT。

**判定结论格式**：`[大需求/小需求] ｜ 触发维度：xxx ｜ 理由：xxx`。

### 前置短路

- 纯加 UT / IT 用例、不改业务 / 生产代码 → 直接判小需求模式。

### 典型可触发（正面示例）

- 新增简单 CRUD / 校验接口（handler 模板 + 简单逻辑，单测全 mock）
- 单个任务内具体业务动作调整（清理 / 判定 / 删除条件）
- 内部重构、日志 / 文案 / 配置类改动
- 单模块内部、局部改动：低风险、可独立回滚

### 排除项（触犯任一 → 标准模式）

| 排除项 | 说明 |
|--------|------|
| 改变已上线接口的请求 / 响应契约 | 下游兼容需真实链路验证 |
| DB schema / 迁移变更 | GORM model 字段增删改 / migration；含存量数据迁移 / 兼容 |
| **核心业务逻辑** | 凡改动会影响核心业务运转的逻辑；识别路径与代码面映射见「项目自定义」区 |
| 并发核心 | goroutine 池、锁、实例并发处理 |
| 跨项目 / 跨模块 / 跨服务 / 复杂异步链路 | UT 无法完整覆盖（外部回调、跨服务编排） |
| 不可逆 / 高风险操作 | 删除、资金、权限、发布类改动 |

**判定口径**：

- 「数据变更」= 数据结构 / 契约变更（动字典），非数据值改动（动值）
- 「需新增测试」= 业务改动引入新的可验证行为；纯加测试不在此列
- 灰色地带（拿不准）→ 判大需求（标准模式）；典型灰色地带：改动引入现有 UT / IT 覆盖不了的新行为、需新增 / 改写用例才能验证

> **核心边界（判断口诀）**：改动的是「写状态」（变更核心数据 / 触发后续处理 / 对外产生副作用）→ 核心，标准模式；改动的是「读状态」（查询 / 校验 / 配置 / 结果获取）或业务内具体动作 → 可走小需求。

### 行数角色

不作判据，仅作汇报信息（"业务逻辑约 X 行"）；业务逻辑 ≤ 50 行为典型，超线时 AI 主动向用户确认一次（"业务逻辑约 X 行，超参考线，确认走小需求？"），用户同意即放行。

### 漏估回退

实际改动触犯任一排除项 → 在汇报 03 结论时同步把 `00-overview.md` Meta `小需求模式` 改回 ⬜，从 04 起按标准模式确认；已按实际发生时间写入的记录不回填。
